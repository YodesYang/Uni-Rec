# 1. 赛题核心
================================================================================

主题：面向大规模推荐的「序列建模」与「特征交互」的统一。

任务：
- 设计统一的 Tokenization 方案与同构、可堆叠的骨干网络（Recommendation Block）；
- 在「单一架构」内同时建模用户行为序列（多域）+ 非序列多域特征；
- 输出对目标广告的 pCVR（Predicted Conversion Rate，点击后转化概率）。

公式：
    pCVR = P( conversion = 1 | Ad, User, Context )

评估指标：AUC（ROC 曲线下面积，越接近 1 越好）。
损失函数：典型为 BCEWithLogits（baseline 默认），可选 Focal Loss。

特殊规则（与常见 Kaggle 比赛差异）：
- 严禁模型集成 / 模型融合（强调架构创新，不允许暴力堆模型）。
- 设两项创新奖（独立于排行榜，各 USD 45,000）：
  · 统一模块创新奖（Unified Module Innovation Award）
  · Scaling Law 创新奖
- 排行榜奖金池总额约 600 万人民币，与 KDD 2026 联合。

# 3. 数据集 Schema（demo_1000.parquet）
================================================================================

(2026-04-10 起为「扁平列布局」：所有特征都是顶层列，不再嵌套 struct/array。)

文件信息：
- 行数：1,000；列数：120；大小 ~39MB（仅作 schema 参考，正式数据量级远超）

120 列分 6 类：
  类别                            列数     dtype                       说明
  ID & Label                       5      int64 / int32              核心标识与标签
  User Int Features               46      int64 / list<int64>         用户整型特征
  User Dense Features             10      list<float>                 用户稠密特征
  Item Int Features               14      int64 / list<int64>         物品整型特征
  Domain Sequence Features        45      list<int64>                 4 个域的行为序列
  ────────────────────────────────────────────────────────────────────
  合计                            120


## 3.1 ID & Label 列（5 列，非空）

  user_id        int64
  item_id        int64
  label_type     int32   ← 行为类型；正样本判定的核心字段（见 §3.6）
  label_time     int64   ← 行为发生时间戳
  timestamp      int64   ← 事件（曝光/请求）时间戳

约定：当 user_int_feats_{fid} 与 user_dense_feats_{fid} 共享同一 {fid}，
      它们对齐描述同一实体/信号（int 描述离散面，dense 描述连续面）。


## 3.2 User Int Features（46 列）

- 标量 int64（35 列）：
  user_int_feats_{1, 3, 4, 48-59, 82, 86, 92-109}
- list<int64>（11 列，多值/multi-hot）：
  user_int_feats_{15, 60, 62-66, 80, 89-91}


## 3.3 User Dense Features（10 列）

- list<float>（10 列）：
  user_dense_feats_{61-66, 87, 89-91}


## 3.4 Item Int Features（14 列）

- 标量 int64（13 列）：
  item_int_feats_{5-10, 12-13, 16, 81, 83-85}
- list<int64>（1 列）：
  item_int_feats_{11}


## 3.5 Domain Sequence Features（45 列，4 个行为域）

  domain_a_seq_{38-46}     :  9 列   （fid 38..46）
  domain_b_seq_{67-79, 88} : 14 列
  domain_c_seq_{27-37, 47} : 12 列
  domain_d_seq_{17-26}     : 10 列

每个 domain 内部包含若干 list<int64> 列，其中：
- 一列是「时间戳序列」（与主样本 timestamp 求差，可做 time-bucketing）；
- 其余列是该序列的 side-info（item_id、category_id、author_id 等）。
- 具体「哪个 fid 是 ts_fid」由 schema.json 中的 cfg['ts_fid'] 指定。


## 3.6 label_type 的语义（重要 · 与 baseline 强相关）

- label_type 是一个 int32，取值多于 0/1，编码不同动作类型。
- baseline (`baseline/dataset.py`) 中正样本定义：
      label = 1   iff   label_type == 2     # 即「转化」
      label = 0   其他所有取值（含 null）
  代码片段（参考定位）：
      labels = (batch.column[label_type].fill_null(0)
                  .to_numpy().astype(int64) == 2).astype(int64)

- 推论与注意事项：
  · 0 / 1 / 2 / ... 这些 label_type 可能分别对应 曝光/点击/转化/其它互动。
  · 训练目标是「点击后转化」（PCVR），因此正负样本定义务必以 label_type==2 为准。
  · 多目标实验时（如 CTR/CVR 联合），可以把 label_type 进一步拆解为多个 0/1 头。

- 转化回流（CVR 任务通病，需要警惕）：
  · 训练数据通常按时间截断，最后几天的 label=0 可能是「假阴」（转化尚未回流）。
  · 经验做法：评估时去掉 tail-K 天，或对 tail-K 天样本做权重 / 延迟反馈建模
    （Delayed Feedback Modeling）。
  · TAAC 2026 评测在线下进行（基于划分好的验证/测试集），但仍需关注训练数据
    的回流截断。

baseline/
├── dataset.py           # PCVRParquetDataset：流式 IterableDataset
│   - 直接读取扁平列 Parquet（不依赖嵌套结构）
│   - 预分配 numpy buffer，融合 padding loop
│   - 时间桶 BUCKET_BOUNDARIES（65 桶，含 padding=0）
│   - 序列截断：seq_max_lens dict（默认 256，可逐 domain 配）
│   - 处理脏数据：null / -1 → 0；OOB id 可 clip 或 raise
│
├── model.py             # PCVRHyFormer 主模型（HyFormer 风格）
│   主要模块：
│   - RotaryEmbedding (RoPE) + RoPEMultiheadAttention
│   - SwiGLU、CrossAttention、TransformerEncoder、SwiGLUEncoder、LongerEncoder
│   - RankMixerBlock（Token Mixing + Per-token FFN）
│   - GroupNSTokenizer / RankMixerNSTokenizer（两种 NS Tokenization）
│   - MultiSeqQueryGenerator（独立 Query token / 序列）
│   - MultiSeqHyFormerBlock（Seq Evolve + Query Decoding + Query Boosting）
│   关键约束：
│   - rank_mixer_mode='full' 时， d_model 必须能整除 T = num_queries*S + num_ns
│
├── trainer.py           # PCVRHyFormerRankingTrainer
│   - Dual optimizer：
│       · Adagrad   → 稀疏 Embedding 参数
│       · AdamW     → 稠密 Dense 参数
│   - Loss：BCE / Focal（focal_alpha, focal_gamma 可调）
│   - 高基数特征 cold-restart：reinit_sparse_after_epoch + reinit_cardinality_threshold
│     （参考 KuaiShou MultiEpoch: https://arxiv.org/pdf/2305.19531）
│   - 评估指标：BinaryAUROC（sklearn）+ binary logloss；NaN 过滤
│   - EarlyStopping + step/epoch 双粒度 evaluate
│   - checkpoint 与 schema/ns_groups/train_config 一并落盘
│
├── train.py             # 训练入口
│   - 环境变量优先：
│       TRAIN_DATA_PATH / TRAIN_CKPT_PATH / TRAIN_LOG_PATH / TRAIN_TF_EVENTS_PATH
│   - 默认 lr=1e-4，sparse_lr=0.05，patience=5，emb_skip_threshold=0
│   - seq_max_lens 默认 'seq_a:256,seq_b:256,seq_c:512,seq_d:512'
│
├── ns_groups.json       # NS 分组配置（GroupNSTokenizer 才需要）
│   - user_ns_groups U1..U7 + item_ns_groups I1..I4（11 组）
│   - 注释强调：是「示例」，需按自己的特征语义重新分组
│
├── utils.py             # logging / EarlyStopping / set_seed / sigmoid_focal_loss
└── run.sh               # 当前激活 RankMixerNSTokenizer，不依赖 ns_groups.json
                         # user_ns_tokens=5, item_ns_tokens=2, num_queries=2

注意（命名约束）：
- baseline 内部使用 `seq_a / seq_b / seq_c / seq_d` 这些 logical 名，
  通过 schema.json 的 prefix 字段映射到原始列名 `domain_a_seq`/`domain_b_seq`/...
- 用户自行制作 schema.json 时务必保证 prefix 与 parquet 列名一致。

# 5. 关键技术方向 / 论文清单（按相关度排序）
================================================================================

## 5.1 OneTrans —— 统一 Tokenizer + Mixed Parameterization
（赛题方向直接对应；datawhale 解读已收藏）

- 思路：S-tokens（序列）共享参数；NS-tokens（非序列）每 token 独立参数。
- Mixed Causal Attention：
    · S-token 因果地相互 attend（建模时间/意图顺序）
    · NS-token 全局 attend 到所有 S-token + 之前的 NS-token
- Pyramid Stack：layer-wise 收缩 query 数量，逐层蒸馏到尾部 NS-token。
- KV Caching（Cross-Request）：用户行为序列 append-only，跨请求缓存 K/V，
  把每次请求 O(L_S) → O(ΔL_S)。
- 离线指标：相对 encode-then-interaction 提升 +5.68% GMV（论文）。

## 5.2 RankMixer —— 硬件感知的同构 backbone
（baseline 中已采用其 NS Tokenizer 思想）

- Multi-head Token Mixing：参数无关、O(T·D) 替代 self-attention 的 O(T²·D)。
- Per-token FFN：每个 token 独立 FFN 参数，避免 dominant feature 淹没长尾。
- Sparse-MoE 变体：每 token 仅激活一部分专家，最少代价扩到 1B+ 参数。
- 工业指标：MFU 4.5% → 45%；抖音 feed 在线 active days +0.3%、in-app duration +1.08%。
- 关键约束：D 必须是 T 的整数倍（baseline 已 enforce）。

## 5.3 HyFormer —— 双向 Query Decoding / Query Boosting
（baseline 实现风格的直接来源）

- Global Tokens 作为「序列 ↔ 异构特征」的语义接口（不做参数级强耦合）。
- 每个 HyFormer 层：
    Query Decoding：Q ← CrossAttn(Q, K_l, V_l)         // K/V 来自序列编码器
    Query Boosting：Q ← MLP-Mixer + Per-token FFN      // Q 与 NS-token 拼接
- 序列编码可选：Full Transformer / LONGER 风格 / SwiGLU 轻量。
- 多序列设计：每条序列独立 Q token 集，靠 Query Boosting 跨序列交互。
- 抖音搜索全量部署，AUC vs LONGER+RankMixer：+0.17%（同 FLOPs 下）。

## 5.4 LONGER（高效长序列编码）
- 用 cross-attention 替代 self-attention：Q 长度 L_H ≪ L_S，Key/Value 取全长。
- 复杂度 O(L_S²) → O(L_H · L_S)。
- baseline 中通过 `LongerEncoder` 实现（top_k 采样最近的 K 个有效 token）。

## 5.5 其他可参考方向
- HSTU / ULTRA-HSTU：生成式推荐架构（未在 HyFormer 论文中作为 baseline 对比）。
- Wukong、DCNv2、xDeepFM：传统特征交互 baseline（性能上界已较低，仅作参考）。
- DIN / SIM / ETA：长行为序列建模经典论文。
- MultiEpoch（KuaiShou，arXiv:2305.19531）：高基数 Embedding cold-restart，
  baseline 已集成。

# 6. 关键经验 / 可改进方向（按预期收益排序）
================================================================================

## 6.1 数据 / 特征侧（性价比高）

- [ ] 复核 label_type 全枚举值与样本占比：是否还有其它 label_type 是「弱正样本」
      可参与 multi-task。
- [ ] 针对 list 类特征做 stats encoding：长度、unique 数、最近一次时间差。
- [ ] 跨 domain 特征 alignment：同一 fid 在 user_int / user_dense 同时出现时，
      联合喂入同一组（baseline 默认是分开的）。
- [ ] 为序列 timestamp 设计更细的桶：当前 65 桶可能在「近 1 小时」内过粗。
- [ ] 检查 OOB id 比例（baseline `dump_oob_stats`）；OOB 比例高 → schema vocab 可能不准。
- [ ] 高基数 sparse 特征启用 `emb_skip_threshold`（默认 1e6）控制显存占用。

## 6.2 模型结构（中等收益）

- [ ] 把 `seq_encoder_type` 从 `transformer` 切到 `longer` 时，确认 top_k 与
      seq_max_lens 配比（top_k 一般取 max_len 的 10%~25%）。
- [ ] num_queries / num_hyformer_blocks 的 scaling：参考 HyFormer Figure 3，
      AUC ~ FLOPs 满足 power-law；先 sweep ×2、×4 再决定。
- [ ] RoPE：当前默认 `use_rope=False`，开启对长序列通常 +0.1% AUC（小心 head_dim
      要够大才不会过度旋转）。
- [ ] RankMixer mode：`full` > `ffn_only` > `none`（一般情况下）；
      `full` 受 D % T == 0 约束，crash 时优先放宽 num_queries / num_ns_tokens。
- [ ] 多任务化：增加一个 `label_type==1` 的 CTR 头，主头依然是 PCVR，
      auxiliary loss 权重从 0.1 起 sweep。

## 6.3 训练 / 优化（小收益但稳）

- [ ] sparse_lr 与 dense_lr 解耦时，sparse 通常 0.01~0.1 的 Adagrad，dense 1e-4 ~ 5e-4 AdamW。
- [ ] reinit_cardinality_threshold > 0 + reinit_sparse_after_epoch=1 复现
      MultiEpoch 效果，长期训练防过拟合。
- [ ] 早停 patience=5 偏紧，长尾收益场景可调到 8~10。
- [ ] Focal Loss：正样本极稀疏（CVR 普遍 < 5%）时尝试 alpha=0.25, gamma=2.0。
- [ ] Mixed precision（bf16）+ torch.compile：吞吐 ~1.3× 起步。
- [ ] eval_every_n_steps：复赛 10× 数据时务必启用 step-level 验证，避免一个 epoch 过长。

## 6.4 工程 / 平台（避免踩坑）

- [ ] Taiji 提交格式与本地一致即可（参考官方知识库）；CKPT 自带 schema.json + ns_groups.json
      已在 trainer 中实现。
- [ ] DataLoader num_workers：单机 8~16 较稳；超过 16 容易 /dev/shm 爆（baseline
      已切 `file_system` 共享策略）。
- [ ] 复赛免费 GPU 8 卡：用 DDP + sparse Embedding 单卡放置即可，不需要 ZeRO-3。
- [ ] schema.json 字段建议加版本号；当官方 demo 数据再次更新时方便回归测试。

## 8.2 [x] 写一份 schema.json 自动生成脚本

实现：baseline/infer_schema.py
关键点：
- 从列名正则识别四类特征（user_int / user_dense / item_int / domain_X_seq）。
- 整型列：vocab_size = max(positive value) + 1（可改为 percentile，见参数）。
- list 列：dim = 实际最大长度（同样可改为 percentile）。
- ts_fid 启发式：序列内某 fid 的正值中位数 > 1e9（典型 Unix 秒级时间戳）。
- 输出 domain_key 用 baseline 兼容的 `seq_a / seq_b / seq_c / seq_d`，
  prefix 字段保留原始 `domain_a_seq` 等列名前缀。

CLI：
  python baseline/infer_schema.py \
      --parquet <file_or_dir> \
      --output  schema.json \
      [--vocab-percentile 1.0] \
      [--dim-percentile  1.0] \
      [--ts-min 1000000000] \
      [--sample-rows 100000]

风险与回归点（拉到正式数据后必查）：
- demo 1k 行可能 vocab_size 严重低估（真实数据上 fid 可能跳到 1e7+）；
  正式数据建议用全量扫描或 --vocab-percentile 0.999。
- ts_fid 启发式失败时（例如某 side-info 也是大数值），手工把对应 domain 的
  `ts_fid` 字段改成正确 fid 即可，schema.json 是纯文本。
- 默认 dim=max 在长尾极端长序列下会撑出大显存；正式数据先用 --dim-percentile 0.99。

  #             num_heads=4, d_model=64, num_queries=2,

  # A. SwiGLU（最低延迟，无 attention）
  bash baseline/run.sh --seq_encoder_type swiglu

  bash baseline/run.sh --seq_encoder_type transformer

  # C. LONGER（折中，cross-attn top_k 压缩）

每组用相同 seed (--seed 42) 跑 ≥3 epoch，记录：
  Val AUC / LogLoss / Params / FLOPs / Step latency / GPU peak mem

期望（参考 HyFormer 论文 Table 1）：
  Transformer ≥ LONGER ≥ SwiGLU （AUC）
  SwiGLU      ≪  LONGER ≪ Transformer （FLOPs）
  LONGER 在初赛 100+ 字段、复赛 10× 数据上一般 ROI 最高。
