> Aux m91 can be dangerously over-optimistic when the mechanism damages primary
> validation or fails clean-window diagnostics. High aux alone is not a public
> selector.

## Hypothesis Shift

The current best family is not "any model with high aux"; it is:

1. train as close as possible to the public-adjacent tail,
2. keep the M106/M119/M123 corrected-T38 + UE61 + DIN backbone,
3. use MTL as a mild regularizer,
4. avoid representation add-ons that hurt primary validation,
5. improve final-training/checkpoint strategy only on the public-positive
   backbone; do not trust one noisy dev slice.

## Priority Lanes

### Lane A · M123-family refinement

Highest probability of small but real gains.

- M137: seed7 freshness + MTL. This fills the cleanest missing cell:
  M119 was seed7 freshness-only; M123 was seed5 freshness+MTL.
- M138 is now rejected: `valid_ratio=0.015` produced a very high internal AUC
  but poor public transfer.
- Future freshness work should stay around public-positive `vr02`/`vr01` and
  use public-validated recipes, not smaller validation windows selected by
  primary AUC.

Expected upside: **+0.0003 to +0.0010** if the public-positive pattern holds.
Probably not enough alone for 0.853.

### Lane B · Final-training / checkpoint strategy

This remains strategically important, but only on the public-positive backbone.
M144 showed that same-run dense-only soup cannot rescue a rejected `vr015/TIN`
mechanism. If platform constraints allow only one checkpoint, useful variants
must be close to M119/M123:

- M141-style `vr02 + MTL + seed7` soup if its internal curve is healthy,
- near-final training that keeps only a tiny selector split but follows
  public-positive M123/M119 recipes,
- fixed-epoch / public-validated checkpoint choices rather than tiny-window
  AUC chasing.

Expected upside: hard to know, but this is one of the few plausible
**+0.0005 to +0.0015** levers without inventing a risky feature branch.

### Lane C · Revisit external UE intel only if implementation changes

Our current implementation concatenates `fid61+fid87` into one UE token and then
optionally adds xitem. The external hint said "feat 61/87" and "as a separate
token"; that might mean **two separate tokens**, not concatenation.

M136 rejects our current 61/87+xitem implementation, not necessarily every
possible interpretation of the intel. A future revisit should test:

- separate fid61 token + separate fid87 token,
- no explicit xitem at first,
- then mild xitem only if primary/clean are healthy.

This is a real code-change lane, but it should not displace M137/M138.

### Lane D · Stop-list

Do not spend more scarce public quota by default on:

- M134/M132: M136 already rejected the shared mechanism.
- M138/M142 and other `vr015` primary-led/soup candidates.
- M143/M144 and TIN-lite in the current classifier-time form.
- High aux-only candidates with weak primary.
- Time-feature variants unless a clean-window diagnostic is green.
- History-CVR, MultiEmbK2, is-missing, encoded-DIN 2.0 in their current forms.
